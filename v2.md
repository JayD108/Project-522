# Jharokha v2: Dual-Screen Host + Hostel Server
*Plan & blueprint · v2.0 · 18 Nov 2026 · replaces the "single screen" parts of v1*

---

## 0. What changed from v1

| | v1 | **v2 (this doc)** |
|---|---|---|
| Screens | 1 (laptop) | **2: laptop panel + external monitor**, swappable with one button |
| Server | none (PWA only) | **Local server in Crostini** for the room + hostel |
| Users | just you | **You + roommate (owners) + invited hostel friends** |
| Daily use | dedicated station | **Shared with Netflix / Prime / YouTube / Google**, so it must step aside when you watch |

The core rule hasn't changed: **video plays in Chrome (hardware decode), never in Linux.** Linux (Crostini) now runs the **server**, which a web page can't do on its own.

> **Terms used throughout**
> - **Layer 1** = the live wallpaper engine (video + ambient effects).
> - **Layer 2** = the command centre (vitals, server info, room widgets).
> - **PWA**: a website installed like an app; gets its own windows and works offline.
> - **Crostini**: ChromeOS's built-in Linux (a container inside a small virtual machine).
> - **Port forwarding**: telling ChromeOS "let other devices on the Wi-Fi reach port X of my Linux server".

## 1. The dual-screen system

### 1.1 Default layout
```
   LAPTOP PANEL (HP, ~15")              EXTERNAL MONITOR (Legion)
 ┌─────────────────────────┐        ┌──────────────────────────────┐
 │  LAYER 2 · Command      │        │                              │
 │  ▸ battery / CPU / net  │        │     LAYER 1 · Live Wallpaper │
 │  ▸ server: users, up    │        │     (+ tiny clock, optional) │
 │  ▸ room board, queue    │        │                              │
 │  [ ⇄ SWAP ]  [ 🎬 CINEMA ]│        │                              │
 └─────────────────────────┘        └──────────────────────────────┘
```
Press **⇄ SWAP**: wallpaper moves to the laptop, command centre moves to the big monitor (with a bigger "wall dashboard" layout).

### 1.2 How it works: swap the content, not the windows
The **Window Management API** lets a web app list the connected screens, open windows on a chosen screen, and go fullscreen on a specific screen (`requestFullscreen({ screen })`). One user click is enough to start a multi-screen layout.

The trick that keeps swapping smooth:
1. At startup (one click), Jharokha opens **two fullscreen windows**: **W-A** on the laptop and **W-B** on the monitor.
2. **Both windows run the same app** and can render either layer.
3. **SWAP doesn't move windows.** It sends one message over `BroadcastChannel` ("A → Layer 1, B → Layer 2"), and each window crossfades to its new layer.
   - Windows never leave fullscreen, so there's no second permission prompt and no flicker.
   - The video **Blob is handed over in memory** (Blobs can be passed through `BroadcastChannel`), so **the HDD isn't touched on swap**.
4. Each layer has **two layouts**, chosen automatically from the screen's size:
   - Layer 2 on the laptop = compact vitals strip. Layer 2 on the monitor = full wall dashboard.
   - Layer 1 on the laptop = 1080p or lower variant. Layer 1 on the monitor = the monitor's native resolution and refresh rate.

> **BroadcastChannel**: a built-in way for windows of the same app to message each other instantly. No server needed.

### 1.3 Living alongside Netflix / Prime / YouTube
You'll often play Netflix on the big monitor, which covers Layer 1. So:
- **Auto-yield:** when a Jharokha window gets covered (the page goes `hidden`), its video **pauses and its memory is released after 2 min**, leaving the decoder and CPU to Netflix.
- **🎬 CINEMA button** (on Layer 2 or from your phone): pauses Layer 1, shrinks Layer 2 to a slim, dim strip, and turns notifications off. Press again to come back.
- **Hotplug:** if the monitor is unplugged, Jharokha drops to single-screen mode (v1 behaviour) and goes back to dual-screen when it's plugged in again (`screenschange` event).
- DRM streams (Netflix/Prime) **can't be captured or re-streamed** to friends. Jharokha only *queues* and *opens* links (see §4).

### 1.4 Fallbacks (decide in Week 0 testing)
| If… | Then |
|---|---|
| Two simultaneous fullscreen windows misbehave on ChromeOS | Use maximized borderless windows + shelf set to *auto-hide* |
| The permission prompt reappears after reboot | A big "Tap to start Jharokha" button (one tap re-creates both windows) |
| Monitor refresh is 144 Hz | Still play 30/60 fps video; never re-encode to 144 |

## 2. Vitals: what we can and can't read

Honest map. ChromeOS deliberately hides low-level hardware from web apps and from Linux.

| Vital | Possible? | Source |
|---|---|---|
| Battery %, charging, time to full/empty | ✅ | Battery Status API |
| **Battery voltage, CPU temperature, fan RPM** | ❌ | Not exposed to web apps. As far as I know, Crostini sees only its own VM, not the laptop's sensors. Shown as "n/a", with a link to ChromeOS's **Diagnostics** app for a manual check |
| CPU load (whole system) | ✅ approximate | **Compute Pressure API**: 4 states (nominal / fair / serious / critical), launched in Chrome 125 |
| CPU/RAM of the server VM | ✅ exact | `/proc` inside Crostini |
| Jharokha's own memory | ✅ | `performance.memory`, `measureUserAgentSpecificMemory` |
| Network: online, type, rough speed, latency | ✅ | Network Information API + server-side pings |
| LAN speed (phone ⇄ laptop) | ✅ | Built-in speed test against our own server |
| Internet speed history | ✅ | Hourly small test from the server (off during Cinema) |
| Screen info (resolution, refresh, which is primary) | ✅ | `getScreenDetails()` |
| **Server vitals:** uptime, req/s, active users, WebSocket count, DB size, disk free, errors | ✅ | Our own server |

> **Compute Pressure**: instead of exact CPU %, Chrome reports a simple stress level. This is good enough for a red/amber/green light, and also tells Jharokha when to cut its own effects.

**"Vitals Ring" widget:** one circle split into Power · CPU · Network · Server. Each arc turns amber or red and shows a reason, e.g. "CPU serious: Netflix + 3 users uploading".

## 3. The room/hostel server

### 3.1 Architecture
```
                    Hostel Wi-Fi (same LAN)
 Phones / laptops ────────────────┐
 (roommate, friends)              ▼
                    ChromeOS Flex  :8080  (port forwarding ON)
                         │
          ┌──────────────┴───────────────────────────┐
          │ Crostini (Debian)                          │
          │  jharokha-server (Node 20, systemd)        │
          │   ├─ Fastify  REST + static web app        │
          │   ├─ WebSocket hub  (live updates)         │
          │   ├─ Yjs sync      (live collaboration)    │
          │   ├─ SQLite (WAL)  users, roles, boards    │
          │   └─ /srv/drops    shared files (quota)    │
          └──────────────┬───────────────────────────┘
                         │ ws://localhost:8080
          ┌──────────────┴──────────────┐
          │ Jharokha PWA (Chrome)        │
          │  W-A laptop · W-B monitor    │
          │  Layer 1 video stays here    │
          └──────────────────────────────┘
```
- ChromeOS **port forwarding** opens a Linux port so phones and other computers can reach it. Any device on the same network then connects at `<laptop-IP>:<port>`.
- The PWA talks to the server over `localhost` (ChromeOS forwards localhost into Crostini automatically).

> **WebSocket**: a connection that stays open, so the server can push updates instantly (new note, someone joined).
> **Yjs**: a library that lets several people edit the same board at once without overwriting each other (a "CRDT").
> **SQLite WAL**: a database mode that writes changes in batches, which is gentler on the HDD.

### 3.2 Hostel network reality (test before building)
| Risk | Why it matters | Check / fix |
|---|---|---|
| **Client isolation** (very common on hostel Wi-Fi) | Phones can't reach the laptop at all | Week 0: open `http://<ip>:8080` from a friend's phone. If it's blocked, room-only access via your own router or hotspot (§3.5) |
| Different floors on different subnets | "Whole hostel" may really mean "your floor only" | Test from 2–3 rooms |
| Laptop IP changes (DHCP) | Bookmarks break | Layer 2 always shows a **live QR code** with the current address |
| Laptop sleeps | Server disappears | ChromeOS power: *while charging → keep display on*; Jharokha holds a wake lock |
| Crostini isn't running after reboot | Server down | Leave a Terminal window open with *Restore apps on startup: Always*. `systemd --user` starts the server when the container boots. Layer 2 shows a red **"Server offline"** badge if it isn't up |

### 3.3 Access & permissions (who can do what)
| Role | Who | Can |
|---|---|---|
| **Owner** | you + roommate | everything: approve guests, control screens, kill switch |
| **Collaborator** | invited friends | edit boards, add to queues, upload drops, request a cast |
| **Viewer** | invited friends | see room status and boards, no edits |
| **Guest (pending)** | scanned the QR | nothing until an owner taps ✅ on Layer 2 or their phone |

- **Invite flow:** the friend scans the QR → enters a name → a request pops up on Layer 2 → an owner approves and picks a role → the friend's device gets a **device token** (stored as an HttpOnly cookie), valid for 30 days and revocable.
- **Big-screen control is owner-only.** Friends can only *request* a cast; an owner approves it.
- **Kill switch:** one button that kicks everyone, closes the port, and turns on Owner-only mode.
- **Quiet hours** (e.g. 00:30–07:00): friends get read-only access; no casts, no sounds.
- **Audit log:** who did what and when, shown on the Layer 2 "Server" tab.
- Rate limits per device; upload quota per user (e.g. 500 MB); max 20 concurrent users.
- **No scanning of the hostel network.** Jharokha only shows devices that signed in to it, never other people's devices.

### 3.4 Security on a shared Wi-Fi
- **v1 (MVP):** plain HTTP on the LAN with device tokens. Fine for boards and queues, but **don't put passwords or anything private on it**, because anyone on the same Wi-Fi could sniff traffic.
- **v2 (recommended):** real HTTPS on the LAN. Buy a cheap domain, point `room.<yourdomain>` at the laptop's LAN IP, and get a Let's Encrypt certificate using the DNS-01 method (no public exposure needed). Friends see a normal padlock with nothing to install. *(This needs a purchase and an account, so I'll ask before setting any of it up.)*
- The server runs as a non-root user inside Crostini, only port 8080 is forwarded, and there's no internet exposure.

> **DNS-01**: a way to prove you own a domain by adding a DNS record, so you can get a real certificate even for a server that's only on your local network.

### 3.5 If the hostel blocks device-to-device traffic
Use a ₹1,000–1,500 travel router or a phone hotspot as the **room network**: the laptop and your phones join it, and the router itself is on the hostel Wi-Fi for internet. Room access works fully; hostel-wide access is replaced by **"visit mode"** (friends join the room Wi-Fi while they're there).

## 4. Feature ecosystem (brainstorm, grouped)

### 🖥️ Screens & ambience
- **⇄ Swap** · **🎬 Cinema** · **🌙 Night Watch** (both screens near-black, faint red clock)
- **Ink theme**: black-and-white brush-ink UI that matches the poster on your wall; HUD elements look painted, and transitions are ink-bleed wipes
- **Scene scheduler** (from v1): Dawn / Deep Work / Ambient / Night
- **Weather-reactive wallpaper**: rain overlay when it's actually raining outside (Open-Meteo)
- **Audio-reactive glow** from the room mic, during Showcase only

### 📊 Command centre (Layer 2)
- Vitals Ring (§2) · server panel · live QR for joining
- **Who's here:** avatars of signed-in friends, with "typing on board…"
- **Approvals tray:** join requests, cast requests, file drops
- Next-class / assignment countdown, exam countdown
- Mini-log of today's events ("Rahul added 2 songs", "Speed test 42 Mbps")

### 🤝 Room & hostel collaboration
- **Room Board**: a shared live whiteboard + sticky notes (Yjs) and a "today's plan" list
- **Door Sign**: room status (*Open / Studying / Sleeping / Out / Gaming*) shown to everyone who has access, set from your phone in one tap
- **Watch-Party Queue**: friends suggest and vote what to watch; owners hit "Open" and it launches on the big monitor (Netflix/Prime/YouTube links). YouTube can even be queued to auto-play next.
- **Cast-to-Wall**: a friend sends a link, image or YouTube video → owner approves → it appears on the monitor for N minutes
- **Drop Zone**: LAN file sharing like AirDrop (notes, PDFs, photos), with auto-delete after 7 days
- **Study Room**: shared Pomodoro; everyone's phone joins the same timer; weekly focus leaderboard on the wall
- **Game Night**: lobby + bracket + live scoreboard on the big screen (there's a controller on the desk 🙂)
- **Hostel Utilities**: polls, a mess-menu board (manually posted), washing-machine timers ("free in 12 min"), lost & found, a borrow ledger (who has whose charger)
- **Split & Settle**: shared room expenses; "settle up" opens a **UPI deep link** (`upi://pay?...`) on the payer's phone. Jharokha never touches money, it just builds the link. (A natural cousin of your mini-UPI project.)

### 📱 Phone superpowers (owners)
- Phone = remote: swap, cinema, scene, volume of effects, approve requests
- **Clipboard & link sync**: send a link from your phone, open it on the laptop with one tap
- "Ping the room": a gentle chime + a message on the wall ("Coming up in 5, open the door")
- **Alarm with sunrise**: the wallpaper slowly brightens before your alarm

### 🧰 Admin & health
- Backups: nightly SQLite snapshot (one sequential write) + weekly export to your Drive *(ask first)*
- **Self-healing**: if the server crashes, systemd restarts it; if a window dies, the other window shows "Tap to restore"
- Thermal guard: Compute Pressure "serious" → drop effects, reduce video to 30 fps, pause speed tests

**Ruled out:** streaming Netflix/Prime to friends (DRM, and against the platforms' terms), reading other devices on the hostel network, an on-device AI model (not enough RAM).

## 5. Hardware budget (with Netflix + server running)

| Item | RAM |
|---|---|
| ChromeOS + Chrome | ~2.5 GB |
| Netflix/YouTube tab while watching | ~0.5–0.8 GB |
| 2 Jharokha windows (video Blob ≤ 300 MB) | ~0.5 GB |
| Crostini VM + Node server + SQLite | ~0.4–0.6 GB |
| **Headroom** | **~3.5 GB ✅** |

**HDD rules (extended from v1)**
- Video: read once per scene → RAM. Swap = zero disk reads.
- SQLite in WAL mode, checkpoints every 5 min; boards are kept in memory and saved to disk every 30 s.
- Drop Zone: per-user quota, sequential writes, a nightly cleanup job.
- Set the Crostini disk to a fixed size (e.g. 40 GB) so it doesn't keep growing.
- No verbose logs: ring buffer in RAM, errors-only file.

**Decode budget:** the laptop's integrated graphics decodes Netflix *and* Layer 1. Auto-yield (§1.3) pauses Layer 1 whenever the monitor is covered, so they don't compete. Use H.264/VP9, never AV1 (from v1).

## 6. Tech stack

| Part | Choice | Why |
|---|---|---|
| PWA (both screens) | Preact + TypeScript + Vite + Workbox | small and fast; offline shell |
| Multi-screen | Window Management API + BroadcastChannel | place windows per screen; instant swap |
| Video | `<video>` ping-pong + Blob in RAM (v1 engine) | hardware decode, no disk thrash |
| Server | Node 20 + **Fastify** + `ws` | fast and simple; you can later port it to Java Spring as practice for your backend goal |
| Live collaboration | **Yjs** + `y-websocket` | conflict-free shared boards |
| DB | **SQLite** (better-sqlite3, WAL) | single file, no extra service, HDD-friendly |
| Auth | device tokens (HttpOnly cookie) + roles table | no passwords to leak |
| Friend web app | same codebase, `/join` + `/room` routes, mobile-first | one build, served by Fastify |
| Process manager | `systemd --user` service in Crostini | auto-start and restart |

**Message flow: a friend casts a YouTube link**
```
Friend phone → POST /cast {url} → server checks role → stores request
→ WebSocket push → Layer 2 tray: "Aman wants to cast ▶ …"  [✅] [✖]
→ owner taps ✅ → server → WebSocket "cast" → monitor window shows it for 5 min
→ audit log entry
```
