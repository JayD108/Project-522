# Jharokha — Live Wallpaper Engine & Ambient Host for ChromeOS Flex
*PRD + Technical Blueprint · v1.0 · Nov 2026*

> **Jharokha** = the carved window in Indian architecture you sit behind and watch the world from. That's the product: a living window in your room.

## 0. TL;DR (the decisions)

| Question | Decision |
|---|---|
| Architecture | **Local-first installed PWA**, fullscreen, auto-restored at login. **No Kiosk. No Crostini in the core.** |
| Video | Chrome's own media pipeline (hardware decode via VA-API), **H.264 or VP9, 1080p**, loop held **in RAM** as a Blob |
| Storage | Video library in **OPFS**, settings in **IndexedDB**, writes batched |
| Phone remote | **WebRTC** data channel, paired by QR code (no server on the laptop) |
| Crostini | Optional "Phase 4 add-on" only, for a LAN-only daemon. Never plays video. |
| Biggest hardware win | Not software: a cheap SATA SSD. Plan works without it. |

## 1. ChromeOS Flex reality check (what I found, and what it forces)

**1.1 Kiosk mode is out.** Kiosk on ChromeOS only works on *managed* devices — it needs a Chrome Enterprise, Education, or Kiosk & Signage licence (~$25/device/yr) plus a Google Admin Console. Screen-signage vendors themselves say Flex kiosk is a poor fit for a single ad-hoc screen. → For one personal laptop, we get "kiosk-like" behaviour without the licence (see 1.4).

**1.2 Crostini can't do video well.** Linux on ChromeOS runs inside a VM + container. Google's own docs list "non-accelerated graphics" for it, and GPU acceleration and video decoding aren't supported in the built-in Linux environment. Crostini on Flex can also be flaky to enable on some machines. And its VM disk image adds extra HDD I/O. → **Video must play in Chrome itself, not in Linux.**

**1.3 The web platform is enough.** Installed PWAs now get **persistent file permissions** for the File System Access API (Chrome 122+): grant access to a folder once, and the app keeps it. Plus OPFS (a fast private file system for the app) and the File Handling API ("Open with Jharokha" from the Files app).

**1.4 How we get "kiosk-like" without Kiosk:**
- Install Jharokha as a PWA → opens in its own window, no browser chrome.
- App calls `document.documentElement.requestFullscreen()` on first tap, and a **Screen Wake Lock** so the screen doesn't sleep.
- ChromeOS setting: *Apps → Restore apps on startup → Always*. Leave Jharokha open → it comes back after reboot.
- Set the device to auto sign-in-friendly (Smart Lock / PIN) so a reboot is one tap.
- ⚠️ Honest limit: ChromeOS **can't use a web page as the real desktop wallpaper**. Jharokha *is* the screen — a fullscreen "host canvas". When you need the laptop for something else, you swipe it away; it's a dedicated station anyway.

> **Terms**
> - **PWA** (Progressive Web App): a website that installs like an app, works offline, gets its own window.
> - **OPFS** (Origin Private File System): a hidden, fast file area only your app can see. Good for storing video copies.
> - **VA-API**: Linux's interface that lets Chrome hand video decoding to the Intel GPU instead of the CPU.
> - **Crostini**: ChromeOS's built-in Linux container.

## 2. Architecture

```
┌──────────────────── ChromeOS Flex ───────────────────────┐
│  Jharokha PWA (fullscreen window)                         │
│                                                           │
│  ┌── Layer 0: Video Engine ───────────────────────────┐  │
│  │ 2× <video> ping-pong ← Blob URL (in RAM) ← OPFS     │  │
│  │ decoded by Intel UHD via Chrome media pipeline       │  │
│  └─────────────────────────────────────────────────────┘  │
│  ┌── Layer 1: Ambient FX (optional) ── Canvas/WebGL ──┐  │
│  │ audio-reactive glow, particles, time-of-day tint    │  │
│  └─────────────────────────────────────────────────────┘  │
│  ┌── Layer 2: HUD widgets ── plain DOM, 1 Hz updates ─┐  │
│  │ clock · weather · calendar · focus timer · net/sys  │  │
│  └─────────────────────────────────────────────────────┘  │
│                                                           │
│  Service Worker (offline shell, API caching)              │
│  Scheduler (scenes, dim/sleep, data refresh)              │
│  Remote Bridge (WebRTC data channel) ◄──── Phone          │
│  Store: OPFS (videos) · IndexedDB (settings, cache)       │
└───────────────────────────────────────────────────────────┘
         ▲ optional Phase 4
   Crostini "host-daemon" (Node) — LAN API, port-forwarded
```

**Why not the alternatives**
- **Kiosk shell:** needs paid licence + Admin Console. Not worth it for one device.
- **Hybrid Crostini + Web as the core:** no GPU video in Linux, extra RAM (VM ≈ 300–600 MB), extra HDD churn, can break on Flex updates. Fine as an *add-on*, bad as a *foundation*.
- **Pure PWA:** everything we need (fullscreen, wake lock, file access, offline, GPU video, WebRTC) is available. ✅

**Hosting:** the PWA must be served from HTTPS once to install (e.g. GitHub Pages under JayD108). After install, the service worker runs it fully offline. *I'll ask you before deploying anywhere.*

## 3. Product: the "Host" feature ecosystem

Design rule: **glanceable from 3 metres, silent, never needs a keyboard.**

### Scenes (the core idea)
A **Scene** = video + HUD layout + FX + behaviour rules. The host switches scenes on its own.

| Scene | When | Feel |
|---|---|---|
| **Dawn** | 6–9 am | warm video, big clock, weather + today's first 3 events |
| **Deep Work** | you start a focus session | dim video, Pomodoro ring, "do not disturb" glow, nothing else |
| **Ambient** | default | full video, tiny corner clock |
| **Night Watch** | 11 pm+ | near-black, faint clock in deep red, video paused |
| **Showcase** | manual | full FX, audio-reactive, for when friends are over |

### Feature list by phase

**Phase 1 — MVP: "It's alive"**
- Video library: import from Files/USB → copied into OPFS, auto-checked for codec support.
- Seamless loop (no black-frame hitch), crossfade between wallpapers.
- Big clock + date, weather (Open-Meteo, free, no API key).
- Auto-dim + pause at night, wake lock by day.
- Fully offline after first load.

**Phase 2 — "It knows my day"**
- Google Calendar (read-only OAuth): next event countdown, "leave in 10 min" pulse.
- Focus timer + Deep Work scene; daily focus-minutes counter.
- Network/system strip: online/offline, connection type, battery & charging, JS memory use.
- Time-of-day colour tint over video (cool at noon, warm at sunset — sunrise/sunset from Open-Meteo).
- Playlist rotation: different video per scene / per hour.

**Phase 3 — "It obeys my phone"**
- Phone remote: scan QR on screen → phone opens a remote page → peer-to-peer WebRTC.
  - change scene / wallpaper, start focus, adjust dim, push a note to the screen ("Back at 6"), "find my phone" ping in reverse.
- **Audio-reactive mode** (mic + Web Audio analyser): video glow/particles pulse with music in the room.
- **Presence-ish idle:** no input + quiet room for N min → Ambient → Night Watch.
- Sticky notes / today's 3 goals, edited from phone.

**Phase 4 — Power add-ons (optional)**
- Crostini host-daemon: LAN-only REST API (no internet signalling), cron-like jobs, home-server pings (show if your other machines/sites are up), market ticker tie-in with your *Nazar* watchlist.
- Voice commands via Web Speech API ("Jharokha, focus 25") — note: Chrome's speech recognition may use Google's servers.
- Generative "living" wallpapers in WebGL (shader skies that follow real weather) — zero disk I/O.

**Ruled out (and why)**
- On-device LLM (Chrome built-in AI / Gemini Nano): needs more RAM/GPU than this laptop has. Use a cloud API from the phone side if ever needed.
- Camera presence detection: works, but constant camera = CPU + privacy cost. Mic level + input idle is enough.

## 4. Hardware strategy (i5-10210U · 8 GB · HDD)

### 4.1 Video decode — let the GPU do it
Intel UHD (Comet Lake, Gen 9.5) hardware-decodes **H.264, HEVC, VP9 (8/10-bit)**. It does **not** hardware-decode **AV1** → AV1 would fall back to CPU = fan noise. Avoid it.

**House encoding standard** (do this on your main PC before importing):
```bash
ffmpeg -i in.mp4 -vf "scale=1920:1080:flags=lanczos,fps=30" \
  -c:v libx264 -profile:v high -preset slow -crf 20 \
  -g 60 -keyint_min 60 -sc_threshold 0 -pix_fmt yuv420p \
  -an -movflags +faststart out_1080p30.mp4
```
- **30 fps default**, 60 fps only for content that needs it (water, particles). Ambient footage rarely benefits from 60, and 30 roughly halves decode work.
- Resolution = panel resolution (don't play 4K on a 1080p screen — pure waste).
- `-an` strips audio (one less decoder running). Fixed GOP (`-g`) makes the loop point clean.
- 20–60 s loops, ~6–10 Mbps → **20–75 MB per wallpaper**.

**Verify on the device:** `chrome://media-internals` → look for `kVideoDecoderName: VaapiVideoDecoder` (or similar hardware decoder). `chrome://gpu` → "Video Decode: Hardware accelerated". The app's import step also runs `navigator.mediaCapabilities.decodingInfo()` and marks files that won't be `powerEfficient`.

### 4.2 RAM-buffered loop — HDD reads once
```
OPFS file ──(1 sequential read)──► Blob in RAM ──► URL.createObjectURL ──► <video>
```
- On scene start, read the whole file **once** (sequential read = what HDDs are good at), keep it as a Blob, play from that. The disk then sleeps.
- Prefetch the *next* scene's video in idle time, max **2 videos in RAM** (current + next), hard cap **~300 MB** total.
- **Seamless loop:** two `<video>` elements on the same Blob URL. ~0.5 s before the end, start B at 0 and crossfade. `requestVideoFrameCallback` times it to the frame. (The plain `loop` attribute can show a hitch.)

### 4.3 RAM budget (8 GB)
| Item | Budget |
|---|---|
| ChromeOS + Chrome base | ~2.0–2.5 GB |
| Jharokha (JS, DOM, decode surfaces) | ~250 MB |
| Video Blobs (current + next) | ≤ 300 MB |
| Headroom | > 4 GB ✅ |
| Crostini (only if Phase 4) | +300–600 MB |

ChromeOS uses compressed RAM swap (zram), so memory pressure costs CPU rather than hammering the disk — but we stay far from that line anyway. Check `chrome://blob-internals` to confirm blobs aren't being spilled to disk.

### 4.4 Zero-thrash HDD rules
1. Videos read **once per scene**, sequentially. Never stream-seek from disk.
2. Settings/stats written to IndexedDB **batched every 5 min** and on `visibilitychange` — not on every tick.
3. Weather/calendar cached in IndexedDB; refresh every 15–30 min.
4. No logging to disk in production builds.
5. Crostini off unless you use Phase 4 (its VM image is a big file on the HDD).
6. Turn off things you don't need on that machine: extra Chrome tabs/extensions, Google Drive offline sync.

### 4.5 Quiet & cool (15 W CPU)
- Keep the **video as a plain `<video>`** with no CSS filters on it → Chrome can hand it straight to the display hardware ("overlay promotion"), the cheapest path.
- HUD: plain DOM, updates **once per second**, no `backdrop-filter: blur` over video (expensive every frame). Use solid translucent panels.
- FX canvas only in Showcase scene; throttled to 30 fps; stopped when hidden.
- Night Watch: **pause video**, release wake lock at your bedtime → ChromeOS turns the panel off. (CSS can darken pixels but can't dim the backlight.)
- Set ChromeOS power to "keep display on while charging" only via the app's wake lock, so the schedule stays in Jharokha's control.
- Target: CPU < 10% average, fan near-silent, during Ambient scene.

> **Terms**
> - **GOP / keyframe interval**: how often the video stores a full picture. Fixed interval = clean loop points.
> - **Overlay promotion**: Chrome sends the video directly to display hardware, skipping extra GPU work.
> - **zram**: swap that compresses memory in RAM instead of writing to disk.

## 5. Tech stack & data flow

| Layer | Choice | Why / trade-off |
|---|---|---|
| UI | **Preact + TypeScript** (or Lit) | tiny (~4 KB), fast; React would work but heavier for an always-on page |
| Build | **Vite** + `vite-plugin-pwa` (Workbox) | easy service worker + manifest |
| Styling | plain CSS + CSS variables per scene | no runtime CSS-in-JS cost |
| Video | `<video>` + Blob URLs + `requestVideoFrameCallback` | uses Chrome's hardware path. WebCodecs is more control but more code and more ways to break the HW path |
| FX | Canvas 2D → WebGL (via `regl` or raw) | only in Showcase |
| Audio | Web Audio `AnalyserNode` on mic | FFT bands drive FX |
| Storage | OPFS (videos), IndexedDB via `idb-keyval`/Dexie (settings, cache) | both survive restarts; call `navigator.storage.persist()` so ChromeOS doesn't evict |
| Remote | WebRTC DataChannel via **PeerJS** (signalling only; data is P2P on LAN) | needs internet for the handshake; Phase 4 daemon removes that |
| Data APIs | Open-Meteo (weather, sun times), Google Calendar API (read-only) | free / no key for weather |
| Optional daemon | Node 20 + Fastify in Crostini, port-forwarded | LAN-only control + jobs |

**Data flow (one scene change):**
```
Scheduler/Phone → "scene: dawn"
  → SceneManager loads scene config (IndexedDB, cached in memory)
  → VideoEngine: Blob already prefetched? play : read OPFS → Blob → play
  → crossfade old → new (0.8 s)
  → HUD swaps widget layout; widgets read from in-memory cache
  → background: prefetch next scene's video, refresh stale data
```

**Folder layout**
```
jharokha/
  src/engine/   video.ts  loop.ts  prefetch.ts
  src/scenes/   manager.ts  scenes.json
  src/hud/      Clock.tsx Weather.tsx Calendar.tsx Focus.tsx SysStrip.tsx
  src/fx/       audioReactive.ts  shaders/
  src/remote/   bridge.ts  (laptop)   remote/ (phone page)
  src/store/    opfs.ts  db.ts
  daemon/       (Phase 4, Crostini)
  tools/encode.sh
```

**Acceptance metrics (v1.0)**
- Loop: 0 visible hitches over 100 loops.
- Avg CPU < 10%, package temp stable, fan inaudible at 1 m (Ambient scene).
- RAM growth < 50 MB over 72 h.
- HDD: zero reads while one scene plays (check with Task Manager / no disk LED blinking).
- Cold boot → Jharokha fullscreen in < 60 s with one tap.

**Risks**
| Risk | Mitigation |
|---|---|
| Flex build lacks HW decode for a codec | import-time `mediaCapabilities` check; re-encode to H.264 |
| "Restore apps" doesn't re-enter fullscreen | app shows a giant "tap to enter" overlay on launch |
| Wake lock released by OS on some events | re-request on `visibilitychange` |
| PeerJS public server down | fallback: manual code pairing; Phase 4 LAN daemon |
| HDD aging / slow boot | optional SSD swap — biggest single upgrade |
